## Priority findings in v0.2

Severity reflects the present local prototype and the impact on later evidence. **High** means incorrect evidence or a broken outcome boundary; **Medium** means a material validation, reliability, or reproducibility gap. No remotely exploitable critical vulnerability was demonstrated.

### V01 — High: malformed responses become harness invalidations and lose their executed response event

**Confirmed.** [workload.py](../etps_v02/workload.py), `decode` (line 24); [runner.py](../etps_v02/runner.py), `answer_from_raw` and `run_offline` (lines 16, 36).

`decode` rejects literal NaN/Infinity but permits numeric overflow: `{"x":1e999}` becomes a Python infinity. It also permits an escaped lone surrogate, `{"x":"\ud800"}`. `answer_from_raw` returns these objects. Encoding the event then raises `ValueError` or `UnicodeEncodeError` before the response event is appended. The slot aborts with `execution_error`, rather than following its malformed-answer branch. Both probes left zero probe events in the journal. In the offline runner the original bytes still exist in the imported script, but the executed observation is missing.

**Fix:** make answer decoding total for bounded arbitrary bytes, reject nonfinite decoded floats and invalid Unicode scalar strings, and keep raw response evidence durable even when projection fails. Use an explicit malformed projection/result rather than serializing an invalid object. Preserve harness/storage errors separately from answer failures.

**Acceptance test:** both inputs are journaled byte-exactly and take the frozen malformed branch; RR remains available for a completed failure/recovery path. Add representative numeric, Unicode, and parser-limit cases. The 1,100-level JSON nesting probe did *not* fail on this Python 3.14 runtime; do not claim that case as a reproduced bug.

### V02 — High: replay does not verify responses against the pinned offline script

**Confirmed.** [runner.py](../etps_v02/runner.py), `replay_slot` (line 86), `replay_export` (line 187).

The plan pins a script hash, but replay verifies only the task graph, raw-answer projection, and journal chains. It never compares probe response status/bytes/telemetry or consumed response count against that script. A bounded fault injection supplied a correct response where the pinned script contained `{}`. Execution and export replay reported accepted=1, `comparison_incomplete=false`, and no warnings, even with `validate_authoring=True`.

This is an internal consistency defect, independent of the acknowledged inability to resist an administrator rewriting all evidence. The test does not claim an external attacker can monkeypatch a deployed process.

**Fix:** replay the slot's pinned response sequence and check each observed response against the corresponding fixture; enforce exhaustion/leftover rules on replay, including valid prefixes for interrupted slots. Persist response index/script identity where useful.

**Acceptance test:** substitutions, reordered responses, changed statuses/telemetry, and omitted/extra scripted outputs cannot become verified finished evidence.

### V03 — Medium: finish and abort metadata are insufficiently verified

**Confirmed for finish records; static for the broader replay policy gap.** [runner.py](../etps_v02/runner.py), lines 86–142; [persistence.py](../etps_v02/persistence.py), `entries` and `append`.

A coherently hashed export declaring `terminal="fail"` and `reason_code="invented"` on an accepting path replays as accepted without warning and repeats the invented reason code. Replay checks an outstanding request and optionally compares resolved obligations, but does not require finish terminal/reason consistency. The append API validates abort codes, while the replay lifecycle does not reassert equivalent abort-payload validation.

**Fix:** define versioned start/request/event/finish/abort schemas; verify the actual reached terminal, declared invalidation code, acceptance/reason relationship, and required v2 fields. Keep legacy omissions explicitly labeled. Share validation between database and export replay.

**Acceptance test:** contradictory terminals, invented codes, and absent required finish fields are rejected or explicitly marked invalid compatibility evidence, never silently accepted.

### V04 — Medium: strict input validation is partial and failures are inconsistent

**Confirmed.** [scorer.py](../etps_v02/scorer.py), `validate`, `finite`; [workload.py](../etps_v02/workload.py), `validate_bundle`, `script_responses`; [__main__.py](../etps_v02/__main__.py).

Examples: a null plan produces `TypeError`; a manifest without `nodes` produces `KeyError`; `finite(10**400)` produces `OverflowError`. The existing intake review also identifies an unhashable `failure` value causing `TypeError`. Several nested mappings, list elements, IDs, and telemetry shapes are used before their types are checked. The CLI has no controlled validation-error boundary, so users get tracebacks.

**Fix:** validate object types, required fields, ID types, nested collections, and numeric ranges before indexing or set membership. Return stable `InvalidRecord` reason codes with field paths. Bound numeric magnitudes and handle integers without implicit overflowing float conversion. Catch expected user-input errors at the CLI and return a concise message/nonzero exit.

**Acceptance test:** a table of null/scalar/list/missing/unhashable fields consistently fails closed through the documented exception/CLI contract, without creating a database.

### V05 — Medium: manifest policy fields can be silently ignored

**Confirmed.** [scorer.py](../etps_v02/scorer.py), `validate` (line 56).

Plan fields are strict, but most manifest/node fields are not. A node containing `budget_seconds=0` passes authoring validation although no budget is enforced. Typos and intended controls can therefore be hashed yet inert. This is particularly hazardous when mapping the missing corpus.

**Fix:** version the executable task schema; separate an explicit non-executable metadata namespace from recognized policy fields. Reject unsupported executable fields and document migration/compatibility behavior. Do not infer that hashing a field enforces it.

### V06 — Medium: authoring validation does not prove executable recovery provenance

**Confirmed.** [scorer.py](../etps_v02/scorer.py), `validate` and `score`.

Changing the fixture recovery's failure reference from `p1` to the future `p2` passes `validate`, then scores `unlinked_recovery`. Other source/obligation linkage defects are similarly deferred to runtime. Duplicate-grant validation is useful but not complete branch-path validation.

**Fix:** check that every reachable recovery path is dominated by source establishment and an eligible linked failed probe for the same obligation. Validate reachable expiration ordering and clearly distinguish intentionally unresolved boundaries. Add preflight branch analysis rather than requiring a run to discover structural defects.

**Acceptance test:** future/unrelated/absent failure authorization is rejected before import; mutually exclusive legitimate branches still pass.

### V07 — Medium: unbounded data and expensive algorithms limit robustness

**Confirmed recursion limit; static complexity analysis for the rest.** [scorer.py](../etps_v02/scorer.py), recursive `visit` (line 115), descendant sets (line 126), byte sets (line 233); [persistence.py](../etps_v02/persistence.py), `append`; [__main__.py](../etps_v02/__main__.py), full-file reads.

A valid acyclic chain of 1,101 nodes raises `RecursionError`. Descendant sets can consume quadratic space; recovery counting materializes individual byte positions; every append rereads/verifies the whole journal prefix. Request records also duplicate full history. Files, scripts, node counts, response bytes, and artifact totals have no explicit admission limits.

**Fix:** establish reviewed input limits; use iterative graph traversal and interval-union counting; use transactional head validation/incremental append with full verification at defined boundaries. Measure journal/history scaling before importing long workloads. No OOM stress test was run.

### V08 — Medium: export completeness is not independently bound

**Confirmed, with an acknowledged trust limitation.** [runner.py](../etps_v02/runner.py), `export_bundle` and `ExportView.entries`.

Replacing a completed slot's exported journal with `[]` produces `attempted=0` with no warnings. It remains an incomplete comparison, so this does not alone forge a complete winning run. The export carries no independently trusted final head/count or global execution-order evidence. Local database heads protect some tail loss; export does not preserve equivalent independent expectations. Per-slot chains also cannot prove cross-slot chronology.

**Fix:** include slot heads and a global ordered ledger in an export envelope to detect accidental truncation and ordering inconsistencies. Independently commit/sign the envelope when evidentiary requirements demand it. Explicitly state that editable hashes alone cannot prevent coherent erasure or prove execution.

### V09 — Medium: implementation identity omits code that changes interpretation

**Static.** [runner.py](../etps_v02/runner.py), `implementation` (line 11).

Only scorer and runner file bytes are hashed. JSON parsing, bundle validation, invalidation policy, and persistence code can change without an implementation mismatch. Python/SQLite versions are not recorded. Raw working-tree source hashes also differ between LF and CRLF checkouts despite identical Git source content.

**Fix:** bind all execution/scoring dependencies and runtime versions through a versioned build manifest. Preserve exact source artifacts; distinguish semantic Git/blob identity from checkout byte identity. Retain the current useful behavior of warning and recomputing rather than silently claiming historical equivalence.

### V10 — Medium: report completeness exceeds what the schema verifies

**Static; known prototype boundary.** [runner.py](../etps_v02/runner.py), `report`; [scorer.py](../etps_v02/scorer.py), `first.setdefault` and terminal acceptance; measurement contract sections 4, 6, 8.

`comparison_incomplete` tests RR availability for planned slots, not paired-arm presence, identical scheduled exposure, required assertions, or budgets. A one-arm plan can be complete by this flag. Branch graphs may skip scheduled content; there is no schedule/recap coverage schema. Acceptance trusts the reached terminal's Boolean. Retention records the first outcome per obligation, not assertion-level or every later obligated-probe correctness. A multi-field wrong answer marks all its obligations failed.

**Fix:** label the existing flag as offline slot-accounting completeness or add separate completeness dimensions. Before live use, freeze and enforce arm pairing, schedule exposure, acceptance assertions, and retention denominators. Do not silently reinterpret historical retention values or invent corpus rules.

## Missing pieces before the intended experiment

These are mostly acknowledged planned work, not regressions. They must not be disguised as implemented features by extra JSON fields or passing synthetic tests.

| Missing capability | What must exist before its relevant milestone |
|---|---|
| Original authored workload | Original byte-exact files, authorship/affiliation/exposure records, task identities, derivation log and semantic review. If permanently unavailable, a separately authorized, separately named new corpus. |
| Full semantic state representation | Reviewed state/version/source authority, valid time, applicability, supersession/current-versus-historical semantics; decide which subset the actual pilot requires. |
| Reviewed answer/acceptance coverage | Corpus-specific answer shapes and alternatives, explicit mandatory assertions/actions, branch coverage, recovery links, recap schedule, and assertion/retention denominators. |
| Calibration release metadata | Fixed numeric counts, paired arms/order, model/configuration versions, stop conditions, frozen external criteria and prior-exposure disclosures. Current offline plan rejects calibration purpose. |
| Actual system adapter | Explicit public/private data boundary; model/memory integration; reset/cache behavior; provider delivery uncertainty, refusal/timeout outcomes and durable attempt handling. |
| Budget enforcement | Request/trial deadlines, retries, output/processed-input/retrieval/storage ceilings and recorded stop reasons. An unrolled graph only bounds branch count. |
| Real timing and processing costs | Declared monotonic client intervals, matching backend generation telemetry when available, ingestion/retrieval/persistence costs and availability reasons. Offline harness speed is not a substitute. |
| Evidence and confirmation | Complete all-attempt ledger and committed calibration manifest; later completed independent manifest/run-start proofs under the adopted attestation policy. Hash chains are not execution witnesses. |
| Validity analysis | Pairwise agreement/reversals against both frozen external criteria, complete acceptance/missingness reporting, later independent review. Unit tests cannot prove neutrality, useful-throughput interpretation, or Nyx superiority. |

## Suggested remediation order

1. **Approve a bounded correctness repair:** V01–V03 first, with focused adversarial regression tests. Preserve raw observations and historical compatibility labels. These repairs do not depend on the missing corpus.
2. **Harden import and replay:** V04–V09, explicit resource limits, versioned schema/implementation identity, and clear evidence trust boundaries. Keep scope proportional to the intended corpus once available.
3. **Correct documentation and protect local data:** G01, G03–G05; add reproducible offline CI under G02. Review the pre-existing intake edits without overwriting their provenance.
4. **Decide the legacy policy:** keep v0.1 as isolated historical code, or separately authorize repairs. Public exposure is blocked on L01–L04 and the result-integrity issues; website/account expansion remains deferred.
5. **Resume corpus intake only with source material:** complete semantic/branch/budget review, then scope the live adapter. Resolve V10's comparison and diagnostic definitions before calibration. Freeze counts/criteria before observing model results.

The immediate next implementation should be the parser/outcome and replay-consistency repair, subject to review of this report. No missing corpus values, calibration counts, or benchmark claims have been invented.
