# eTPS Measurement Contract v0.2

Authorship/provenance: Codex generated this document's wording. User requirements and explicit endorsements are distinguished from model proposals in [PROVENANCE](PROVENANCE.md). Unless that register states otherwise, detailed operational clauses are model-proposed and remain under review. User delivery of review text does not establish its human authorship. Agreement and internal consistency are not empirical validation.

Status: draft 3, 2026-09-14. Consolidates the user's authoritative checkpoint, replacing the earlier strict first-attempt gate with binary terminal acceptance. Sections 2.1 and 5.1 propose detailed closure of the remaining governance, comparison and span-matching issues; these details are not yet approved or empirically validated. Baseline: axendo79/eTPS, main, ea51ce82e011c7e65bdc43e9d5af923cdcec4897. Earlier counterexample and timing-review documents are historical review material where they conflict with this draft. No implementation or v0.1 result conversion is implied.

## 1. Scope and claim

Measure user reconstruction burden under externally specified retention obligations, alongside correctness and throughput. Remain system-agnostic. No memory architecture, vendor, or particular storage mechanism receives preferential treatment.

Candidate index: `eTPS = TPS_raw × (1 − RR)`.

This index has throughput units, but is NOT established as useful output per second or end-to-end task productivity. An input fraction discounts an output rate without a demonstrated causal conversion between them. Draft counterexamples disprove that stronger interpretation. Preserve the formula only as a conditional reconstruction-discounted generation index if further review justifies its usefulness. Until then, report its value as experimental and never use it alone to rank systems.

Specifically, eTPS is a composite index: generation throughput discounted in proportion to the share of newly delivered user input classified as recovery. It is not the observed rate of a separately measured useful-token stream. RR and TPS retain all information used by the index when reported side by side. Whether the index earns a reporting role is separate from choosing RR's denominator. eScore and all further factor aggregation remain deferred; v0.1 composition is not inherited.

Website, leaderboard, account profiles, SEIT, additional quality multipliers, and implementation repairs are outside this stage.

## 2. Authority and freezing

The versioned benchmark specification defines reconstruction, valid obligations, token accounting, correctness rules, and admissible profiles. A frozen task/corpus manifest declares workload-specific obligations, answer keys, branches, and budgets before execution. Evaluated systems/vendors declare capabilities and configuration only. They cannot alter obligations, classifications, keys, or scoring rules for a scored run.

Canonical designation requires a named specification owner, named corpus authors, a publicly recorded review by someone independent of the evaluated vendor and profile authors, conflict disclosures, and a frozen release identifier/hash. These roles are not yet appointed for v0.2: this draft and its future pilot corpus are non-canonical. A vendor may submit a profile; vendor-authored profiles remain explicitly non-canonical under this proposal. Hashing establishes immutability, not fairness or independence.

Release records include spec/profile/corpus versions and content hashes, authorship and review provenance, freeze time, scorer/tokenizer versions, and configuration. Any substantive correction creates a new version; preserve prior records, mark affected results, and rerun all comparison arms. No retroactive relabeling of a scored run.

Candidate workload profiles: session, long-context, persistent-memory, agent-task. They may change task obligations, reset boundaries, and budgets, but not RR semantics. Compare only within the same frozen profile/corpus and compatible measurement boundaries. Unsupported capability means disclosed nonparticipation or observed failure, never deletion of an obligation.

### 2.1 Author identity and comparison prohibition — proposed operational clauses

System affiliation includes authorship, maintainership, employment, funding and direct financial interests in any evaluated component, including a memory layer. It applies to individual developers as well as commercial vendors. A person who authors the profile and develops Nyx has an author-system conflict even if Gemini is the underlying model in both arms. A company rename, a separate repository, or delegation to a model does not remove that conflict.

Disclose the same person's roles in the release and every result record. The initial profile authored by Nyx's developer is developer-authored and non-canonical; this is not a bar to exploratory evaluation. Model assistance is also disclosed but does not substitute for independent governance. Review does not retroactively turn this profile into an independently authored one. Any later canonical corpus requires a separate release under the benchmark's independent governance, with an auditable derivation and conflict review. No claim that those governance conditions are currently met is authorized.

The specification prohibits ranking, pooling, normalizing, or claiming a score improvement across different profile IDs/versions or corpus releases. A shared formula, tokenizer, or hardware configuration does not remove this prohibition. Descriptive presentation is permitted only in separately labeled non-comparable series, without cross-profile score deltas or winner claims. Any new common comparison design must freeze a single profile/corpus and rerun every arm; post-hoc rescaling is not a substitute. This rule applies to RR, experimental eTPS, correctness and task-performance summaries as benchmark claims, not to unrelated hardware specifications.

Every result binds to exactly one profile ID/version/content hash and corpus release/hash. This prohibits combining the same system's metrics from different profiles into a single result, even without a cross-system ranking. A system tested under several profiles publishes several separately identified results.

Before the controlled experiment, independently recorded publication must attest the manifest hash, followed by an externally recorded run-start reference to that hash. The evidence must allow an outside party to establish publication order without trusting project-controlled timestamps. Local file dates, author-supplied commit dates and a commit hash alone are insufficient. Selected mechanism: OpenTimestamps with completed Bitcoin-backed proofs; see [attestation decision](ATTESTATION_DECISION.md). No stamp or attestation has been executed in this task. The proof establishes commitment existence, not public full-text availability or witnessed execution. Ordering evidence does not prove absence of undisclosed prior experiments. The owner authorizes a docs-only commit and push before manifest freeze. That publication must exclude manifest, corpus task files, tokenizer lock, token goldens and their hashes. Freeze-before-run remains mandatory.

The manifest record must separately include a signed or attributable prior-exposure disclosure: declarant, declaration date, workload/corpus version, whether prior runs are known to exist (`yes`, `no`, or `unknown`), known dates/counts/configurations, model-assisted or manual workload inspection, and resulting revisions. Unknown details remain explicitly unknown. This statement is self-attested, not externally verified merely because its hash was timestamped. Preserve disclosures across versions; exploratory, aborted and invalidated executions are not excluded from known prior-run counts. Preparing paper fixtures is disclosed as workload inspection, not misrepresented as executing a model run.

Publication sequence: pre-freeze documentation may be committed and pushed now under user authorization, excluding corpus artifacts and their hashes. Later manifest publication requires its own reviewed artifact set and completed external attestation before any run-start record and execution. The earlier manifest-first/docs-after ordering is superseded by explicit user instruction.

## 3. Established state and obligations

Established state is a manifest-designated proposition delivered through its specified source event, not a statement the system chose to acknowledge. A system cannot avoid obligations by declining acknowledgment. Failed harness delivery makes the run invalid; acknowledged delivery followed by forgetting is a system outcome.

Each state record contains a stable ID and version, value or proposition, source event and authority, establishment event, valid-time interval, applicability predicate, update/supersession relationships, and retention obligations. Valid time describes when a proposition applies in the task world; event order describes when the system learns it. Do not conflate them.

Obligations use ordered event boundaries `[begin, end)`: begin is after delivery of the establishment event; end is before the designated expiration event takes effect. A source introduction cannot count as its own reconstruction. Explicitly identify checkpoints and current versus historical queries. Superseding a current value does not erase historical obligations unless the manifest explicitly ends them.

Contradictory sources do not automatically supersede one another. The manifest must encode source precedence or an unresolved state with an expected uncertainty/clarification answer. Process or retrieval provenance may identify duplication; it cannot create evidential support. Ground truth must be independent of the evaluated system's memory representation.

## 4. RR and token accounting

Candidate definition: RR is the fraction of measured input attributable to user re-supply of benchmark-designated established state after the applicable retention obligation has begun and before that obligation has expired or been superseded.

Recovery requires an observed failure on the same active retention obligation and a frozen branch authorizing that re-supply. The trace must link the recovery event, failure event, probe and obligation IDs. An unrelated earlier failure does not authorize recovery. An unnecessary request for already obligated state counts only when the frozen predicate identifies it as failure of that obligation. Intent is not inferred from wording. A scheduled voluntary or defensive recap has no qualifying failure/branch linkage, contributes no R, and contributes its newly delivered text to I. Unprompted does not itself mean voluntary: an authorized scripted correction after a wrong answer can be recovery even if the model never requested it.

For the controlled pilot, the harness alone selects user-event templates using the frozen branch policy; model/memory-arm identity is not a branch input. An operator cannot choose to restate more or less, edit recovery text, or shorten recovery based on the treatment. Unscripted intervention is a protocol deviation: retain the trace and identify the comparison as invalid rather than retroactively assigning a convenient class. Any replacement trial follows the predeclared invalidation policy, with every attempted trial disclosed. Scheduled recaps must be fixed across arms and separately identified because they can supply answers or dilute RR. A recap-assisted task cannot establish unaided retention across the recapped interval.

Script fixity is a contract requirement: the scheduled contribution is constant across arms and only authorized recovery may vary the user-input denominator. Execute the same scheduled events even after an early answer failure when the protocol can continue; an abort prevents full schedule exposure and must be reported as a truncated failure, not a completed comparable RR trace. Results are scoped to retention under the declared recap schedule. A recap that prevents a failure is indistinguishable in the observed trace from one that was unnecessary; no post-hoc rule may infer that counterfactual.

Let `I` be benchmark-token counts of all newly delivered user-role event payloads in the complete measured task, counted once at first delivery. Include introductions, normal requests, legitimate clarification, new evidence, scheduled recaps, and actual recovery messages. Exclude transport wrappers, system/developer instructions, replayed history, assistant output, tool/retrieval content, and internal memory injections. Report these excluded input costs separately. Include all executed recovery branches and fixed termination rules; do not stop accounting early because a score looks favorable.

Let `R` be the union of token indices assigned to designated recovery spans in those events, where the referenced state obligation is active and applicable. Count a token once even when it references multiple obligations. `RR = R / I`, with integer `0 ≤ R ≤ I`. If `I = 0`, RR and candidate eTPS are unavailable, not zero. Reject negative/nonfinite/inconsistent data; do not clamp invalid records into plausible scores.

A whole trial with no newly delivered user input has I=R=0 even if it processes prior context or generates output. Its RR is undefined (0/0); other available observations remain reportable. A single empty-input turn does not make the whole trial undefined when earlier measured user events contribute I>0. The accounting window is the complete declared trial, never chosen after observing results.

The release must pin one benchmark tokenizer, its version/artifact hash, UTF-8 text normalization, and boundary behavior. Tokenize each complete user payload once. Annotate UTF-8 byte spans. Both endpoints of every designated recovery span must exactly match boundaries in the complete-payload tokenization. Count the union of wholly contained token indices. Misaligned spans fail authoring validation and block freeze; runtime occurrence makes RR unavailable as a protocol defect. Never expand, round, trim or silently count zero. This replaces the draft 2 intersection rule before any token goldens or scored runs. Record this boundary convention and include a mixed-span boundary fixture. Model-native input counts are additional telemetry, not interchangeable denominators. Selected authoring convention: cl100k_base with tiktoken 0.12.0 and ordinary-text encoding; the tokenizer declaration remains unpublished pending artifact verification. This is not Gemini native accounting. Artifact verification and token goldens remain blocked; no numeric RR is claimed.

RR is tokenizer-relative. Comparable RR uses the same declared measurement tokenizer and normalization across all arms, including comparisons of different models. Otherwise label the figures non-comparable across tokenizer definitions. Even a same-model comparison must verify the measurement tokenizer configuration is identical; model identity alone is insufficient. The invariant is that R is a verified subset of the same tokenized input used for I. Multiple inspection/counting passes are permissible if they reproduce that representation and subset; the number of passes is not a validity criterion. Neither replayed prefill nor cache savings changes this input-side denominator.

Recovery text and span annotations are authored before execution, including a fixed rule for whether correction framing is included. Proposed rule: count state-bearing re-supply spans only; report whole recovery-message tokens separately. New facts embedded in a correction are not old-state reconstruction. Canonical pilot messages should separate these clauses to minimize boundary effects.

For mixed messages, the frozen template maps recovery byte spans to state/obligation IDs and identifies the newly introduced content separately. Fixed code verifies template identity, branch provenance and active obligations, then applies the token-span rule. The entire new user payload enters I; only the union of eligible token indices enters R. A designated recovery span cutting a token is invalid even if byte offsets are valid UTF-8 boundaries. Revise the message or its semantically justified designation before freeze, then retokenize the entire payload; do not silently absorb new content to obtain alignment. Whole-token alignment is a mechanical precondition, not proof that the designation is semantically correct. Missing or ambiguous annotations block the fixture from the mechanical pilot; no evaluator may repair them during scoring.

## 5. Mechanical classification and answer checking

The pilot uses finite structured answers with frozen allowed values and normalization rules. Exact structured equality checks complete propositions, including negation, scope, time, and required uncertainty. A response containing a correct keyword alongside the wrong value must fail. Missing fields, incompatible extra claims, malformed responses, refusals, and explicit unknown answers take frozen branches; no live judge decides reconstruction.

Each probe has a finite branch map: correct answer → continue; incorrect/unknown/malformed answer → specified recovery or terminal failure. Branch priority and maximum retries are fixed. A clarification response is valid only at a manifest-designated ambiguity checkpoint. An unsolicited request for obligated information takes the failure branch. Arbitrary free-form dialogue is out of scope for this deterministic pilot; do not claim its semantics can be classified mechanically from keywords.

Every reachable probe must have a total outcome policy. Evaluate outcomes in frozen order: transport/deadline failure; invalid response encoding/schema; expected correct or permitted clarification answer; explicit unknown/refusal if the schema defines it; all remaining schema-valid answers as incorrect. Each outcome has a next event or bounded terminal failure, including exhausted-retry and failed-recovery outcomes. Do not infer refusal intent from unrestricted prose. Empty/malformed/refusal/unknown responses and timeouts are system outcomes, not automatically protocol invalidations. Ambiguous transport delivery follows a predeclared delivery rule with uncertainty recorded; never invent successful delivery.

The final catch-all branch prevents unfamiliar model answers from making the controller's policy undefined. A controller lacking a required branch is a protocol defect; it is not evidence that the evaluated system caused invalid measurement. Off-script user text remains a separate protocol deviation. More observed retention failures should select more authorized recovery or bounded failure paths, not require an operator to improvise variants. A scheduled terminal timeout can end a failed trial without invalidating its observed accounting; truncated exposure still prevents a complete-workload comparison under the proposed completeness rule.

The scorer joins each observed recovery event to its frozen template and triggering branch, verifies active obligations and span membership, then counts tokens. Evaluated systems never receive private answer keys or branch labels. Adapters may see public prompts and allowed state only; harness and memory stores must not expose scorer metadata.

### 5.1 Span designation and finite paraphrase matching — proposed operational clause

The pilot supports only enumerated paraphrases, not open-ended semantic matching. Every recoverable proposition has a stable state/version ID and a finite set of complete user-message variants authored before execution. Each variant includes its exact UTF-8 payload, content hash, half-open byte spans `[start,end)` for state-bearing re-supply, associated obligation IDs, and separately designated new-content spans. Offsets must fall on UTF-8 character boundaries. Authors declare equivalence in advance; fixed code verifies membership, not the truth of that equivalence declaration. Corpus review must therefore attack wrongly declared aliases.

The re-supply predicate accepts a variant only if: (1) its complete delivered payload exactly matches the frozen bytes and hash; (2) its ID is the variant selected by the frozen schedule; (3) its prior failure links to the same obligation and an allowed branch; (4) the obligation is active and applicable at delivery; and (5) every counted span is designated for that obligation. All conditions are necessary. A matching phrase without provenance is not recovery. Tokenize the actual delivered text, not a shorter canonical paraphrase, using the shared measurement tokenizer and exact-boundary convention in section 4.

No case folding, whitespace cleanup, Unicode normalization, fuzzy distance, embedding score, or judge model is applied implicitly. Text normalization is identity for variant matching. Any alternative spelling, spacing, Unicode form or phrasing must have its own frozen payload and spans. Answer-key normalization is a separate declared operation and cannot change delivered-input accounting.

Use one recovery variant per branch in the first pilot. If variant coverage is tested, assign variants by a predeclared trial/branch schedule identical across arms; selection cannot depend on model identity, response verbosity or an operator choice. Enumerated aliases must preserve proposition, negation, time, applicability and source authority. Different lengths legitimately change R and I, so unrestricted selection among aliases is prohibited.

An unmatched user payload is a protocol deviation with unsupported recovery classification: retain exact bytes and metadata, mark RR unavailable for the affected trial, and do not silently count it as R=0 or repair it during scoring. A model's unsupported answer is different: it follows the frozen answer-failure branch and does not invalidate an otherwise faithful harness run. This asymmetry prevents systems from escaping failures by emitting unrecognized answers.

Example designation: `The code is amber. Also sort the list.` has recovery span `[0,18)` covering `The code is amber.`; byte 18 is a separating space; new-content span `[19,38)` covers `Also sort the list.`. An alternative `Use amber as the code. Also sort the list.` needs its own offsets and full-message ID. These illustrate the format, not approved corpus keys; actual offsets and semantic equivalence must be checked before freezing. Separator whitespace belongs to I, but does not by itself qualify for R; a recovery endpoint cutting a token causes validation failure under the exact-boundary rule.

## 6. Correctness before efficiency credit

Report task correctness as correct mandatory final assertions / total mandatory final assertions. Report retained-state correctness as correct first-attempt obligated probe assertions / total obligated probe assertions, before any recovery. Also report counts, per-task outcomes, and post-recovery correctness separately. Zero eligible probes means retained-state correctness is unavailable, not 100%.

Acceptance is binary at the trial boundary under the frozen recovery policy: all mandatory terminal assertions and required action constraints must pass within the declared budget. A successfully recovered trial may be accepted while failing first-attempt retention; preserve both observations. A confidently incorrect terminal answer is not accepted, including when R=0. Invalid measurement and valid task failure are distinct statuses. Retries remain within the trial, which contributes at most one accepted completion.

TPS and RR are primary. Experimental eTPS may be reported conditionally for accepted, measurement-valid trials with available TPS and RR, accompanied by acceptance rate/counts and retained-state correctness. This is not validation of the index. Do not assign failed trials a discounted success score or omit their failures, costs or available RR. Partial correctness is diagnostic and never a formula multiplier. The prior strict first-attempt gate is superseded by the user's checkpoint.

## 7. Throughput and costs

Raw generation TPS requires measured generation-token counts and matching generation-time intervals from reliable instrumentation. Record exact boundaries, inclusion of first-token work, token scope, and whether internal reasoning tokens are observable. Aggregate matching intervals as sum(tokens) / sum(seconds). If generation timing is unavailable, raw TPS and candidate eTPS are unavailable.

Client-observed output tokens / request wall time is response throughput, not raw generation TPS. Streaming arrival intervals are not automatically backend generation timings. Report request latency, time to first token where observed, complete task wall time, and response throughput separately, with declared clock and boundaries. Missing API usage must remain unavailable; never estimate tokens from word counts for scored data.

Task wall time starts before the first task-related operation and ends after required completion/persistence work. Record preparation separately, including preloaded state and ingestion. Include task retrieval, updates, retries, and storage writes in task cost accounting; record overlapping spans without summing them twice. Report retrieval latency/calls/tokens, internal input tokens, storage bytes/writes, billed cost where available, and timeout outcomes. A lower RR does not demonstrate that memory cost is justified.

eTPS does not directly measure retry cost. A retry without new user re-supply can leave RR unchanged and may leave generation TPS unchanged even while total time and processing increase. Report attempt counts for every trial, attempts per accepted trial as a labeled conditional summary, end-to-end task latency, and total processed input/output tokens per trial with their native counting scope and availability. Replayed provider input counts belong to that processing telemetry, not I. Keep missing usage unavailable. Do not modify RR or add a multiplier to force all retry costs into the index.

## 8. Repetition, reporting, and reproducibility

Freeze trial count, tasks, order/randomization, seeds where supported, retry rules, timeouts, reset behavior, and exclusion rules before running. Preserve every attempted trial, including failures. Do not pool unlike profiles.

Publish trial-level TPS, experimental eTPS or unavailability reason, RR, R, I, correctness counts, gate status, timing/cost data, and full configuration. Compute a candidate only from that trial's paired measurements. Do not multiply separately aggregated medians. For an even sample size, median is the arithmetic mean of the two middle values. If CV is reported, label sample standard deviation / arithmetic mean, unavailable for fewer than two observations or zero mean. Never call range/median CV.

Retain RR for every measurement-valid trial with I>0, including failed trials, and disclose complete versus truncated schedule exposure. An accepted-only RR or experimental eTPS summary must be explicitly conditional and accompanied by acceptance counts/rate, failure outcomes, and first-attempt retention. Acceptance is not multiplied into eTPS.

Every RR summary reports planned, attempted, measurement-valid, RR-available and RR-unavailable trial counts, with individual unavailable reasons and unattempted/aborted outcomes. Undefined zero-input ratios and protocol deviations are distinct reasons. Missingness is not assumed random: an available-subset RR is not a complete-workload RR. Proposed first-pilot completeness rule: zero RR-unavailable trials, full planned-trial accounting and full required schedule exposure are necessary for a complete-workload comparison; otherwise report an incomplete comparison with diagnostics. This threshold must be settled and frozen before scoring. Expected zero-input edge fixtures are scorer-validation cases, not silently included/excluded to improve a workload score. Unexpected model answers remain valid measured failures unless independent evidence establishes an actual protocol fault.

Freeze both the number of scheduled paired pilot runs and the task-trial count per arm before execution, with stable IDs, run order, stop conditions and the treatment of unattempted work. A pilot run is one scheduled execution of the declared task set for the comparison arms; a task trial may contain bounded internal retries. Freeze the actual numeric counts in the manifest; none is selected by this draft. Do not keep launching replacement pilots until a complete or favorable result appears. Preserve and disclose every attempt, aborted run, invalidated comparison and available trace. Stopped runs include explicit unattempted slots; never pass them off as completed trials.

If either arm has unavailable RR, publish `comparison_incomplete`, reason-coded deviations, affected run/trial IDs and arm, acceptance and retention observations, costs, available component measurements and exposure coverage. Do not describe the other arm as the winner or an available subset as full-workload performance. A measured retention failure remains evidence about that answer; the protocol gap explains the missing comparison and does not itself prove a memory-layer benefit. Arm-concentrated missingness is reported, not treated as random. Where RR is available but another prerequisite fails, label that missing prerequisite separately.

A correction to branches, recovery variants, answer keys or other frozen protocol content requires a new manifest version/hash and new independent freeze evidence before rerunning both arms under the revised protocol. Preserve old attempts and link the new release to its predecessor with the defect and change disclosed. Never retroactively rescore repaired content as if it were the old frozen manifest, reuse old-arm results as the new comparison, or mix versions to complete a run. Partial old results may remain labeled historical diagnostics. Valid scored failures alone do not require corpus revision.

Any claim about eTPS ranking validity must record an independently defined objective, frozen before scoring, with its version/hash, parameters, conversion assumptions, tested domain and comparison rule. Do not choose or adjust it to favor the index. List each reversed pair individually, including point IDs, measured components and both orderings; a reversal rate alone is insufficient. State agreement against a declared reference or as a pairwise map. Distinguish the tested domain from demonstrated agreement and label sampled/inferred boundaries estimated. A whole-region claim requires support for the relevant comparisons throughout that region. No current objective or agreement region has been validated.

Initial reporting uses trial vectors and paired differences; no universal cross-task eTPS aggregate is authorized. A separately labeled pooled RR uses sum(R)/sum(I) for an identical task set, not an unweighted average of ratios. Publish eligibility and failure counts alongside all summaries; no winner claim from survivors alone.

Replay records preserve exact delivered payloads, event ordering, templates/branches, responses, normalized answer results, token offsets, obligation transitions, raw timing/usage, errors, configuration and artifact hashes. Recomputing from these records must reproduce classifications, counts, gates, and unrounded arithmetic. Round only for display. This is a future persistence requirement, not a claim about the current logger.

## 9. Later controlled experiment

Compare the same pinned Gemini model/configuration alone and with a memory/state layer. Use identical base tasks, prompts, decoding settings, answer rules, timing definitions, and budget ceilings. Actual recovery paths may differ according to the same frozen policy; forcing identical recovery prompts would destroy the burden comparison. Retrieved context also differs by treatment and must be logged, counted, and budgeted.

Declare context truncation, retrieval access, storage ceilings, reset/cross-session rules, cache policy, endpoint version stability and run order. Prohibit answer-key access. Attribute differences to the tested configuration; do not generalize to all memory systems. The memory arm may lose on correctness, reconstruction, latency, or cost. Report these tradeoffs without importing memory-architecture-specific scoring dimensions.

System energy per accepted task is withheld whenever backend energy coverage is unavailable. The Gemini comparison therefore has no system-energy result unless complete coverage is established. Local retrieval energy may be reported solely as separately labeled component telemetry, never a proxy total or lower-bound system score.

## 10. Work sequence and release blockers

1. Review the proposed finite-variant span predicate, author-system identity rule and cross-profile prohibition, including their adversarial cases. Do not treat model-authored closure proposals as accepted merely because they are written here. Settle them before building the corpus; select the shared tokenizer and concrete budgets before numeric scoring.
2. Freeze a small documentation/data corpus with all requested cases. Each manifest needs state IDs/versions, sources, updates, applicability/validity, obligation intervals, structured expected answers, branch/recovery templates and spans, budgets, termination, and expected classification outcomes.
3. Hand-replay counterexamples and verify independent readers derive identical labels. A remaining judgment call blocks a mechanical-scoring claim.
4. Only after those reviews, repair scorer/runner/persistence in small changes with adversarial fixtures and replay checks. Do not start infrastructure or publish rankings.

No dependencies, API credentials, virtual environment, or model calls are needed for steps 1–3. Install only the selected tokenizer and test requirements when implementation begins. No commit or push is authorized.


Calibration policy: the first pilot estimates variability and protocol coverage; it is not a confirmatory superiority test. Freeze its actual count after corpus authoring and before execution. A later separately frozen manifest uses the disclosed calibration findings to specify a meaningful effect, planning method and new comparison count; do not reuse calibration outcomes as fresh confirmatory trials.


Tokenizer release binding: record the encoding definition identity independently of its accessor package version, plus the exact lock-file SHA-256. Different lock hashes prohibit RR comparison. The frozen manifest must include the exact bytes/hashes/lengths of token goldens and the tokenizer lock, not merely package names or intended settings. Goldens are reproducibility fixtures, not independent semantic validation. The draft 3 exact-boundary decision supersedes intersection-based expected outcomes in older paper reviews.
